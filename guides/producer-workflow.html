Producer Guide ​

One guide for web producers: daily workflow, guards, and (optional) assessment for 4 producers (2 per brand).

Use this sectionWhen
Daily workflow (below)Your main reference: pull → status → refresh → push → reports.
Quick StartFirst-time setup: install, then make status (runs setup if no config).
Multi-ProducerWorking with a partner on the same brand (2 per brand).
Ecomm (Smartsheet)Smartsheet/ecomm workflow and data flow.
Assessment for 4 producersOptional: fit, gaps, and recommendations for teams moving from manual.

Start with Quick Start, then use the daily workflow below. If you share a brand with another producer, see Multi-Producer. For Smartsheet/ecomm, see Ecomm (Smartsheet).

Principle: Use Make Only ​

You do not need to run node directly. All producer commands are:

bash
make <command>
1

make help shows the full list. If a developer asks you to run a Node script, ask them to expose it via make instead.

Overview ​

Wireframe → refresh → push to staging. Building happens automatically (make pull auto-builds new dates). Run make refresh to rebuild selected refreshes. The changeout email is generated automatically after push. Excel time-only values are interpreted as UTC; the CLI shows dates and times in your local time.

Entry point: make status is the main entry point. On first run with no configuration, it runs setup (view/edit config), then continues to the dashboard. It’s your dashboard. It shows what’s live, synced, ready to push, or needs a build. When the wireframe has start and end times, status shows which refresh is on the homepage right now (Current live) and displays time ranges on each row so you can see which refresh covers which period. Picking a refresh from the status picker sets it as your active refresh, then you choose an action (Build refresh, Push, Upload, Delete, Refresh detail, Pull) from the same screen.

Core flow:

make pull  →  make status  →  make refresh  →  make push  →  make reports OP=report DATE=...
1

Building happens automatically: make pull auto-builds new dates after fetching. Run make refresh when you need to rebuild selected refreshes. make reports OP=report DATE=... provides per-refresh zone/IPID visibility before or after push.

You don't need to change configs or templates in normal use—the developer manages those. You don't need to type dates or refresh numbers: after make pull you run make status and pick your working date once; the app remembers it (sticky selection) for make refresh, make push, and the rest. Flags like DATE= or REFRESH= are for testing and automation, not daily use.

Starting Your Day ​

Step 1: Status or Pull ​

bash
make status
1

or

bash
make pull
1

make status is the single entry point: if you have no config, it runs setup first, then opens the hub. make pull fetches data and auto-builds (does not open status — run make status after). Pull does three things:

  1. Git pull — syncs your local files with the rest of the team
  2. Fetch — parses the latest Excel/Smartsheet into refresh data (progress: "Fetching data … Parsing {file}")
  3. Auto-build — builds only dates that don't have a build yet (progress: "Building new dates …" or "All dates already built")

Use arrow keys to move, Enter to select a refresh. That becomes your sticky working date for all following commands. From the same screen you can run an action (Refresh detail, Build refresh, Push, Upload, Delete, Pull) or press q to exit.

Producer thinking & blocking errors

After pull: "Got the data. Now I'll pick the date I'm working on."

Step 4: Replicate (manual) ​

After push, replicate from staging to production in SFCC Business Manager. The CLI no longer has a separate replicate command.

Switching Dates ​

Via status (preferred) ​

bash
make status
1

Pick a different refresh from the dashboard — use arrow keys to navigate, Enter to select. That selection becomes your active refresh, then choose an action (preview, push, etc.).

Direct set ​

bash
make status DATE=2026-02-14
1
  ✔ Selected 2026-02-14 (Valentine's Day)
  Status: · NEW — needs make pull
1
2

Override for one command ​

Core commands accept DATE= to override the sticky selection without changing it:

bash
make refresh DATE=2026-02-10    # Build 02/10 without switching
1

Switching Data Source ​

To switch between local Excel and Smartsheet:

bash
make setup
1

Choose Edit configuration and select your data source. Next make pull will fetch from the new source. Switching to Smartsheet requires SMARTSHEET_API_KEY in .env (your developer sets this up). To switch back to local, run make setup again and choose Local Excel file.

Switching OCAPI (SFCC Sync) ​

To check whether OCAPI sync is enabled:

bash
make doctor
1

Shows OCAPI: enabled or disabled. To toggle: run make setup, choose Edit configuration, and toggle the OCAPI option. Pushing to SFCC requires the SFCC env vars in .env.

Force Rebuild Flow ​

After a template edit (e.g., fixing a typo in the homepage HTML):

  1. Run make status and pick the refresh
  2. Choose "Force rebuild" from the action menu
  3. Then choose "Push to staging" (use make push FORCE=1 if the refresh was already synced)
  4. Optional: run make reports OP=report DATE=... to audit zone/IPID details

Managing assets for SFCC brands ​

How assets are managed: When you run make push, the CLI syncs campaign content to SFCC for the current brand (loft or ann). Each zone in your wireframe has an action (LAUNCH, UPDATE, REMOVE, NO_CHANGE). Push creates new content assets (LAUNCH), updates existing ones (UPDATE), or removes them from SFCC (REMOVE). That is how producers manage assets day to day—by editing the Excel/Smartsheet and pushing.

Per brand: Configuration is one brand at a time. Data, refreshes, and the asset registry (which tracks current asset IDs per zone) live under dev-env/{brand}/. To work on the other brand, run make switch (toggle) or make switch BRAND=ann (or make setup). Each brand’s assets in SFCC are separate.

Dev / advanced: If a developer needs to push only asset HTML (no campaign/slot changes) or remove a refresh from SFCC and local:

  • make upload — Upload content assets only for the selected refresh (hotfix).
  • make delete DATE=... — Remove a refresh from SFCC and local (cleanup, cancelled campaigns).

For visibility and auditing, use reports:

  • make reports OP=report DATE=... — Per-refresh launched zone/IPID table.
  • make reports OP=history ARGS="--zone=..." — Zone change timeline.

See upload, delete, and reports for details. For normal producer workflow, make push is enough.

Appendix: Assessment for 4 producers ​

Optional reading for leads: fit and gaps for 4 web producers (2 LOFT, 2 Ann Taylor) moving from a manual process. Daily how-to is in the sections above.

Fit: Single flow (pull → status → refresh → push → reports), sticky date, auto-builds, build/sync guards, data quality before push, multi-producer safety via Git. No need to touch configs/templates in normal use.

Gaps to know: (1) One brand per config—use make switch (toggle) or make switch BRAND=ann or make setup if working both. (2) Data errors fixed in Excel/Smartsheet, then make pull and retry. (3) Multiple refreshes (r1, r2): use picker or REFRESH=r2 / ALL=1. (4) Replication is manual in Business Manager (no CLI command). (5) First-time: make setup and env vars—see Quick Start. 2 per brand: own machine and sticky date; always make pull first. Force rebuild: make status → "Force rebuild" action → make push (use FORCE=1 if already synced).

DimensionAssessment
Fit (2 per brand)Good: sticky date, guards, Git sharing, clear flow.
Transition from manualGood: one linear flow, data quality, preview; source of truth = Excel.
