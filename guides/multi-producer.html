Multi-Producer Guide ​

How two web producers share work on the same brand without stepping on each other. For the full daily flow (pull, preview, push, commit), see Producer Guide. Note: make push auto-generates the email.

The Setup ​

  • 2 producers per brand (e.g., Producer A and Producer B both work on LOFT)
  • Everything shared via Git — refresh files, build outputs, sync status
  • Each producer has a personal sticky selection (date/r#) — stored in dev-env/.ocapi-config.json under brandState.{brand}.currentDate (gitignored)

The Rules ​

Rule 1: Always Start with make pull ​

This syncs your local files with everything your partner committed. Without it, you're working on stale data.

bash
make pull    # ALWAYS first
1

Rule 2: Pick Different Dates ​

After make pull, the dashboard shows which dates exist and their status. Coordinate with your partner — don't both work on the same date.

  1. ● 02/08  NFP 70 / FP 50%        LIVE
  2. ✔ 02/10  NFP 60 / FP 40%        READY   → push
  3. ○ 02/12  EP 50%                  BUILD   → preview
  4. · 02/14  Valentine's Day         NEW     → preview
1
2
3
4

"I'll take 02/12, you take 02/14."

Rule 3: Build Guards Protect You ​

If your partner already built and synced a date, make preview will tell you:

  ⚠  2026-02-10 was already synced on 2026-02-09T16:45:00Z
     Use: make status  to pick another date
     Use: make status → "Force rebuild"  to force rebuild (rare)
1
2
3

You can't accidentally overwrite their work. The guard reads the refresh.json sync section which your partner committed.

Rule 4: Commit After Every Push ​

After make push (which auto-generates the email), immediately commit and push to Git:

bash
make commit       # git add + git commit
git push          # share with teammate
1
2

This ensures your partner sees the updated refresh.json (with sync section) on their next make pull, which activates the build guard.

How It Works ​

Sticky Selection is Personal ​

When you run make status DATE=2026-02-12/r1, it writes to dev-env/.ocapi-config.json under brandState.{brand}.currentDate. This file is gitignored — your partner never sees it, and it never causes merge conflicts.

Your partner can have their own currentDate set to 2026-02-14/r2. You each work independently.

Handling Conflicts ​

Merge Conflict on Git Pull ​

If make pull shows a merge conflict:

  ❌ Merge conflict. Resolve manually.
1

This usually happens when both producers edited the same file. Resolve it with standard Git:

bash
git status                       # See conflicting files
# Edit the conflicting files
git add .
git rebase --continue
make status                      # Verify everything looks right
1
2
3
4
5

Both Producers Fetched New Data for the Same Date ​

This is fine. writeJsonSafe in the filesystem store compares content before writing — if the data is identical, the file isn't touched. If the data changed (e.g., Smartsheet was updated), the newer fetch wins, which is correct since Smartsheet is the source of truth.

One Producer Needs to Re-Push a Date ​

If a date was synced but needs a correction:

bash
make status DATE=2026-02-12      # Select the date, then choose "Force rebuild"
make push                        # Re-syncs to SFCC
make commit                      # Save updated refresh.json (sync section)
git push
1
2
3
4

Communicate with your partner before doing this — they should make pull before working on any date that was just re-pushed.

Commit Conventions ​

Keep commit messages consistent so git log is readable:

loft 2026-02-12 done           # Normal completion
loft 2026-02-12 force-rebuild  # Template fix after initial sync
ann 2026-02-14 done            # Ann Taylor completion
1
2
3

To see recent activity:

bash
git log --oneline -- dev-env/*/refreshes/
1
