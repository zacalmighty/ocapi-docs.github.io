Producer Review: 4 Web Producers (2 per Brand) ​

Assessment of the application for 4 web producers (2 LOFT, 2 Ann Taylor) who previously used a manual process. For the actual daily flow and setup, use Producer Workflow and Quick Start. See Producer guides overview for how all producer guides fit together.

Who They Are ​

RoleCountBrand(s)Old Way
Web Producer (LOFT)2LOFTManual Excel → manual HTML/copy → manual SFCC upload or campaign setup
Web Producer (Ann Taylor)2Ann TaylorSame

Manual way (before this tool): Producers would typically take wireframe data (Smartsheet/Excel), build or copy content into HTML or SFCC by hand, upload assets, configure campaigns and slots in Business Manager (or similar), then send changeout emails. Error-prone, repetitive, and hard to coordinate when two people work the same brand.

Fit Summary ​

The app gives them a single flow (pull → build → preview → push → done → commit), sticky date, build/sync guards, data quality checks before push, and multi-producer safety via Git. Strengths: no need to touch configs/templates, guards prevent overwriting a partner’s work, and the full how-to lives in Producer Workflow and Multi-Producer Guide.

Gaps and Risks (Manual → Tooling) ​

1. Brand is global, not per-producer ​

  • Reality: dev-env/.ocapi-config.json has one brand (and one Excel path). The Makefile uses BRAND ?= (from config).
  • Risk: If Producer A (LOFT) and Producer B (Ann) work on the same machine (e.g. shared dev box), they must remember make switch TO=... or they’ll run commands for the wrong brand.
  • Mitigation: Docs already say “Wrong brand → make switch TO=loft/ann”. For 2-per-brand, usually each person has their own machine and stays on one brand; switching matters for backups or multi-brand producers.

2. “Fix in Excel and re-fetch” can feel slow ​

  • Reality: Data quality errors say “Fix the issues in the Excel and re-fetch with make pull.”
  • Risk: Producers used to fixing things in SFCC or in local HTML may expect to fix in the repo and re-push. The tool enforces “source of truth = Excel/Smartsheet” and re-fetch.
  • Mitigation: Ecomm workflow doc explains that the wireframe is source of truth; producers need to know that data fixes go in Excel/Smartsheet, then make pull and rebuild.

3. Multiple refreshes per date (r1, r2) ​

  • Reality: Some dates have r1, r2; if they only pass DATE=, the CLI uses sticky or prompts. Non-interactive (scripts/CI) must pass REFRESH=r# or ALL=1.
  • Risk: A producer who runs make push DATE=2026-02-14 in a script or from a cron might get “multiple refreshes: r1, r2” and no push.
  • Mitigation: Docs (push, reference) already say: “If REFRESH is omitted on a multi-refresh date … interactive refresh picker (TTY) … explicit error in non-interactive (provide REFRESH or ALL=1).” Producers in TTY get the picker; they just need to know that DATE=… REFRESH=r2 is required when not using the picker.

4. Replicate is still manual ​

  • Reality: make replicate opens a checklist for STG → POD; it does not perform replication itself.
  • Risk: Producers might expect “make push = staging, make replicate = production” to be one click. It’s intentional that production is a separate, manual step.
  • Mitigation: Quick start and push docs say “Production deployment requires manual replication via make replicate”; producer workflow and multi-producer guide reinforce that.

5. First-time setup and credentials ​

  • Reality: make setup configures brand and OCAPI toggle; SFCC credentials are env vars (SFCC_BASE_URL, SFCC_CLIENT_ID, etc.). make health verifies.
  • Risk: New producers (or a new machine) must have env set; otherwise push fails with auth/OCAPI errors.
  • Mitigation: Quick start says “make setup” then “make pull”; troubleshooting and push say “OCAPI not enabled → make setup, make health.” A short “first day” checklist (see below) would help.

6. Terminology: “SFCC already has this date” ​

  • Reality: After the recent change, when nothing is new to sync the message is “SFCC already has this date; no changes to sync” (and slot binding is skipped).
  • Risk: Producers who are used to “Already synced” might look for that exact phrase; docs and CLI are aligned on the new wording.
  • Mitigation: Producer workflow and multi-producer docs should use the same phrase where they describe the “no second push” behavior (see recommendation below).

Recommendations ​

For product/docs ​

  1. First-day checklist lives in Quick Start: clone, npm install, make setup, set SFCC env vars, make health, then make pull → pick date → build → preview → push. Add “If you work both brands, use make switch TO=ann / make switch TO=loft” there if not already present.

  2. Emphasize “fix in Excel, then make pull”
    Data quality errors are fixed in the Excel/Smartsheet; then run make pull and try make push again. Producer Workflow and troubleshooting already state this; keep it in one place (e.g. Producer Workflow).

  3. Multi-refresh
    For a date with multiple refreshes (r1, r2), use the interactive picker or pass REFRESH=r2 (or ALL=1). Documented in push and Commands Reference.

For the 4 producers ​

  • 2 per brand: Each producer runs on their own machine, sticky date is personal, build/sync guards protect the other. Always make pull first and make commit + git push after push/done.
  • If someone covers both brands: Use make switch TO=... and run make status to confirm brand before building/pushing.
  • Manual legacy: They no longer hand-edit HTML for standard flows or manually create campaigns in BM; the tool generates and syncs. Hotfix path: edit template → make edit → make push (and optionally FORCE=1 if already synced).

Summary ​

DimensionAssessment
Fit for 4 producers (2 per brand)Good: sticky date, guards, Git-based sharing, clear flow.
Transition from manualGood: one linear flow, data quality before SFCC, preview; need clear “source of truth = Excel” and first-day setup.
Brand switchingDocumented; matters only if one person works both brands.
Multi-refresh datesHandled via sticky + picker or REFRESH= / ALL=1; docs are adequate; one consolidated sentence helps.
Replicate / productionBy design manual; docs state it.
Docs consistencySmall fix: use “SFCC already has this date” in producer-facing docs where the push guard is described.

The application is well-aligned with 4 web producers (2 per brand) moving from a manual build/deploy process, with minor doc and onboarding tweaks recommended above.
