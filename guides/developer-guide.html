Developer Guide ​

How the CLI is built and how to add or change behavior. For architecture detail, see Architecture.

Architecture overview ​

The app uses Clean Architecture-style layers:

LayerLocationPurpose
CLIsrc/cli/Entry point, command routing, flags, output
Applicationsrc/application/usecases/Workflows (Excel, Dev, SFCC, Reporting, Health)
Domainsrc/domain/Entities (Campaign, ContentAsset, SlotConfiguration), validation
Infrastructuresrc/infrastructure/File system, OCAPI client, parsing, rendering, registry

The CLI is thin: it parses arguments, builds a BrandContext, and delegates to use cases.

CLI entrypoint ​

  • Bootstrap: src/cli/index.js loads environment (dotenv, logger, MOCK_DATE) and hands off to Commander.
  • Command routing: src/cli/program.js defines every command via wrapAction(), which resolves the brand and target, builds a BrandContext, and calls the matching handler in src/cli/commands/.
  • Makefile as source of truth: The app is controlled only via make (e.g. make pull, make push). The Makefile is the canonical interface; see Commands Reference for the Make variable → CLI flag table.

Command structure ​

  • Handlers: One file per command under src/cli/commands/ (e.g. handleRefresh.js, handleSync.js).
  • Pattern: Each handler receives (brand, target, options, ...). It uses resolveRefreshForCommand or similar when it needs a single refresh, then calls a use case on brand.usecases.*.
  • Adding a command: See Adding a new command below.

Adding a new command ​

  1. Register in program.js: In src/cli/program.js, add a new .command() block and use wrapAction('handleMyCommand', { ... }) to wire it up. wrapAction handles brand resolution, BrandContext creation, and handler dispatch automatically.
  2. Create the handler: Add src/cli/commands/handleMyCommand.js. The handler receives (brand, target, options) from wrapAction. Use resolveRefreshForCommand if it needs a refresh, then call the appropriate use case via brand.usecases.*.
  3. Use case (if needed): If the command needs new business logic, add a use case in the right workflow directory under src/application/usecases/ and expose it through BrandContext.
  4. Make target (optional): In the Makefile, add a target that runs $(CLI) myCommand $(BRAND) ... with the right flags.
  5. Document: Add docs/cli/my-command.md and link it from Commands and Commands Reference.

BrandContext and dependency injection ​

  • BrandContext (src/application/context/BrandContext.js) is the composition root: it holds the brand id, file store, SFCC config, and usecases (Excel, Dev, Sfcc, Reporting, Health).
  • Handlers receive a BrandContext instance; they don't construct use cases themselves. This keeps the CLI testable (you can pass a mock or test brand).
  • Config is loaded from sfcc.config, slots.config, and user config (.ocapi-config.json, .env).

Barrel files (index.js re-exports) ​

Directories with multiple modules use barrel files (index.js) to simplify imports. Instead of importing from individual files, consumers import from the directory:

// Instead of:
const { ApiClient } = require("./ApiClient/ApiClient");

// Use the barrel:

OCAPI runtime configuration ​

All OCAPI tuning constants (rate limits, retries, timeouts, cache TTL) are centralized in OCAPI_RUNTIME in src/config/sfcc.config.js. These are hardcoded constants -- not environment variables -- to ensure consistent behavior:

Token persistence ​

OAuth tokens are cached to dev-env/.token-cache.json by AuthService so that consecutive CLI invocations reuse the same token instead of authenticating each time. The token is refreshed 60 seconds before expiry. See Environment Setup for details.

Testing strategy ​

  • Unit tests: Under tests/ — config, domain, infrastructure, usecases, utils (strings, dates, ipid, path, excel helpers). Vitest; include pattern tests/**/*.test.js.
  • CLI tests: Under tests/cli/ — command routing, guards, prompts. Use mocks for file system and OCAPI where needed.
  • Integration: tests/integration/workflow.test.js and similar for full flows. When dev-env is not populated (e.g. in CI), workflow tests use tests/fixtures/workflow/refresh.json so they always run.
  • Workflow (end-user flow): Use make fresh-install for a clean reset (dev-env + node_modules) followed by a full test run.
  • Test commands (Makefile is source of truth): See Commands Reference. Summary: make test (run all), make test-watch (watch mode), make test-coverage (coverage report), make check (lint + tests + audit for CI), make test-sync DATE= (push to OCAPI with --yes --force for CI / non-interactive). To run a subset: npx vitest run tests/domain or npx vitest run tests/cli.

Code conventions ​

  • Lint: ESLint (see .eslintrc.json). Run npm run lint or make check (lint + tests + audit).
  • Format: Prettier (see .prettierrc). Run npm run format.
  • JSDoc: Used for public APIs and for generating API Reference. Run make docs-build to regenerate API docs.
