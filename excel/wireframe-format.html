Wireframe format ​

The wireframe is the source of truth for all campaign content. This page defines the format the CLI expects when preparing or editing the Excel file.

Supported Excel formats ​

The system auto-detects the format based on column headers:

BANNERLegacy LOFT formatHas WEB_PROD_CODED, DEVICE with date patterns
FLAT_TIMEDTimed refreshesHas REFRESH_DATE, START_DATETIME, ACTION

Example: one row → one asset ​

A single child row with ACTION=LAUNCH, ASSET_TYPE=PPH, ZONE=PPH, COPY=50% off winter becomes one content asset in the refresh JSON under assetsByType.PPH. After build, it appears in the PPH template output and in the OCAPI payload for that slot.

Excel rows (CONVERTED format):

Resulting structure in refresh.json (simplified):

  • campaign.refresh.date = "2026-01-26", campaign.refresh.name = from parent row.
  • assetsByType.HOMEPAGE.zones = one zone object with zone: "HP_HERO", items: [{ action: "LAUNCH", copy: "50% off winter", destination: "/sale/winter", ... }].

After building (triggered automatically by make pull for new dates, or by make preview if stale), each zone gets rendered HTML and an asset ID (and IPID for LAUNCH). The OCAPI payload then includes these assets and their slot bindings.

Dates and times: Excel vs status board ​

The status board shows a Date/time column and a Name column. They come from different Excel columns and can look different if your sheet uses date prefixes in the name or midnight UTC times.

SourceExcel column(s)What it controls
Folder / row dateDATE / REFRESH DATEThe refresh's logical date: folder path (refreshes/YYYY-MM-DD/r1) and row ordering on the status board.
NameREFRESH NAMEThe Name column on the status board (e.g. "2/20: $39 FP PANTS / STYLE EVENT EP 40"). The prefix 2/20: is just text.
Date/time columnSTART_DATETIME, END_DATETIME (optional)The live window (when the campaign is "live" on the site). Converted to local time for display (e.g. 2/19 7pm – 2/19 7pm).

So:

  • Name can include a date like 2/20: (the "go live" day in the label). That does not set the live window.
  • Date/time on the board = startTime–endTime from the refresh, shown in local time. If you leave start/end blank, they are inferred from the refresh name (e.g. @3PM) or from the next refresh's start; if you use midnight UTC (2026-02-20T00:00:00.000Z), they will show as the previous calendar day in US timezones (e.g. 2/19 4pm or 7pm depending on zone).

To have the status Date/time match the date in the Name (e.g. "2/20" in both):

  • Use START_DATETIME / END_DATETIME (or the TIME column where supported) with the intended go-live time in the correct timezone (e.g. 7pm ET on 2/20), so that the displayed window lines up with the date in the name.

Multi-day windows: A refresh can run across several days (e.g. "2/20 60% off" live from 2/20–2/22). Put the actual start and end datetimes in START_DATETIME and END_DATETIME (full date+time, e.g. from Excel or ISO). The parser uses those values from the file as-is, so the status Date/time column will show the correct range (e.g. 2/20 7pm – 2/22 11pm in local time).

When the sheet has dates properly entered (SFCC format) ​

If the sheet has REFRESH_DATE plus START_DATETIME / END_DATETIME (or full datetime cells), the pipeline keeps them in the format SFCC expects:

  1. Parser — Reads the sheet and normalizes to ISO 8601 (e.g. 2026-02-19T19:00:00.000Z). Time-only values (e.g. 7:00 PM) are combined with REFRESH_DATE; full datetimes (e.g. Excel date+time or ISO strings) are used as-is. Result is stored in refresh.json as campaign.refresh.startTime and endTime.
  2. Build / OCAPI — When building the campaign and slot configurations, those same ISO strings are passed through as start_date and end_date on the campaign and on each slot's schedule. No extra conversion is done.
  3. SFCC — OCAPI expects schedule.start_date and schedule.end_date in ISO 8601. The payload sends them in that form, so SFCC receives exactly what the sheet specified (in UTC).

So: enter dates (and, if you want a specific go-live time, START_DATETIME / END_DATETIME or a full datetime). The system keeps everything as ISO 8601 from the sheet through to SFCC. Times in the sheet (e.g. 19:00 or 7:00 PM) are interpreted as UTC when combined with the date unless you use a full datetime that already carries timezone (e.g. an ISO string with Z or offset).

Current setup: If you use the conversion script (original → CONVERTED), when the original has no time the script now writes default START_DATETIME 19:00 and END_DATETIME 23:59 into the CONVERTED file so it is already in proper form. Use that CONVERTED file as your source (activeSource: local); the next pull/build will produce ISO 8601 through to SFCC. You can still override by putting times in the original (e.g. in the refresh label or in time columns) or by editing the CONVERTED file.

IPID format ​

IPIDs (Internal Promotion IDs) are used for analytics tracking.

Structure ​

The system builds every IPID from exactly these eight segments, in order:

{brand}_{page}_{device}_{zone}_{position}_{promo}_{destination}_{date}
1

Segment reference (canonical) ​

SegmentPlaceholderDescriptionExample values
1. Brand{brand}Brand key (no cross-brand)loft, at
2. Page{page}Page / asset typehp, pph, popup, plp
3. Device{device}Device / audienceall, mobile, desktop
4. Zone{zone}Zone within the pagehero1ta1, main, hp-2t
5. Position{position}Item position in zone (1-based)1, 2, a
6. Promo{promo}Promo/copy slug or npsale50, 30offsuiting, np
7. Destination{destination}Destination slugsaleviewall, suits, na
8. Date{date}MMDDYY (6 digits only)012626, 012026
  • Date segment: Exactly MMDDYY (6 digits). No other date format is used for IPIDs.
  • Brand segment: loft or at only. No cross-brand use: LOFT assets must use only loft_ IPIDs; Ann Taylor assets must use only at_ IPIDs.

Examples ​

IPIDBreakdown
loft_hp_all_hero1ta1_sale50_saleviewall_012626LOFT, homepage, all audiences, hero zone, 50% sale, Jan 26 (MMDDYY: 012626)
at_pph_all_pph_1_30offsuiting_suits_012026Ann Taylor, PPH, all, 30% off suiting, Jan 20 2026 (MMDDYY: 012026)

Best practices ​

  • Lowercase only
  • Underscores as separators
  • Date at end: MMDDYY only (6 digits)
  • No cross-brand: Use the correct brand prefix for the current run
  • Be consistent across refreshes

Multiple refreshes per day ​

If you have multiple refreshes on the same day:

  1. Include time in the refresh name: "1/26 3AM Site Changeout"
  2. The system assigns ordinals automatically: r1, r2, r3...
  3. Use the TIME column for precise scheduling

Multiple sheets ​

The system scans all sheets in the workbook and uses the first one that matches a known format.

Priority order: CONVERTED > BANNER > FLAT_TIMED

To force a specific sheet, run: make excel ARGS="--sheet='Sheet Name'"

Validation checklist ​

Before saving your wireframe:

  • [ ] All required columns present (REFRESH NAME, DATE, ACTION, ASSET TYPE, SITE LOCATION or SITE_LOCATION — both accepted)
  • [ ] Actions are valid (LAUNCH, UPDATE, REMOVE, NO_CHANGE)
  • [ ] Dates in a format Excel parses (e.g. M/D/YYYY)
  • [ ] No empty rows breaking parent-child grouping
  • [ ] IPIDs follow naming convention (see Validation and fixes)

Common issues ​

Rows not parsing ​

Check:

  • Is there a parent row with REFRESH NAME and DATE?
  • Are required columns present?
  • Are there merged cells breaking the structure?

Wrong asset type ​

Check:

  • Is ASSET TYPE spelled correctly?
  • Is SITE LOCATION filled in?
  • Does the zone name match expected patterns?

Dates not recognized ​

Check:

  • Use M/D/YYYY format (1/26/2026)
  • Avoid text formatting on date cells
  • Check Excel is interpreting as date, not text
