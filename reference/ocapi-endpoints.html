OCAPI Integration ​

This document describes how the application integrates with Salesforce Commerce Cloud (SFCC) via the Open Commerce API (OCAPI).

Request Lifecycle ​

Every OCAPI request passes through the ApiClient, which handles rate limiting, authentication, and automatic retries for transient failures.

Postman collection: how endpoints should work ​

The file sfcc-ocapi.postman.json defines the Payload Workflow (No Batch). Endpoints should work in this order:

StepRequestMethodURL pattern
01 - AuthGet OAuth TokenPOST{AUTH_URL} (e.g. https://account.demandware.com/dw/oauth2/access_token or .../dwsso/oauth2/access_token) — body: grant_type=client_credentials, Basic auth = client_id:client_secret
02 - PayloadValidate Payload + Site AccessGET{base_url}/s/-/dw/data/{api_version}/sites?client_id={SFCC_CLIENT_ID}
03 - WorkflowPUT Campaign from payloadPUT{base_url}/s/-/dw/data/{api_version}/sites/{site_id}/campaigns/{campaign_id}?client_id={SFCC_CLIENT_ID}
03 - APUT Content Asset (per asset)PUT{base_url}/s/-/dw/data/{api_version}/libraries/{library_id}/content/{asset_id}?client_id={SFCC_CLIENT_ID}
03 - BPUT Slot Config (per slot)PUT{base_url}/s/-/dw/data/{api_version}/sites/{site_id}/slots/{slot_id}/slot_configurations/{config_id}?context=global&client_id={SFCC_CLIENT_ID}
03 - CPUT Slot Binding (per slot)PUT{base_url}/s/-/dw/data/{api_version}/sites/{site_id}/campaigns/{campaign_id}/slot_configurations/{slot_id}/{config_id}?context=global&client_id={SFCC_CLIENT_ID}
04 - VerifyGET CampaignGET{base_url}/s/-/dw/data/{api_version}/sites/{site_id}/campaigns/{campaign_id}?client_id={SFCC_CLIENT_ID}
04 - VerifyGET Sample AssetGET{base_url}/s/-/dw/data/{api_version}/libraries/{library_id}/content/{asset_id}?client_id={SFCC_CLIENT_ID}

Variables: base_url = SFCC_BASE_URL, api_version = SFCC_API_VERSION (default v21_10), site_id = SFCC_SITE_ID, library_id = SFCC_LIBRARY_ID. For library path, use URL-encoded library ID (library_id_encoded in Postman). All data API requests use Authorization: Bearer {access_token}.

Architecture Overview ​

Service Layer ​

The application uses four OCAPI services, located in src/infrastructure/sfcc/OcapiServices/ (barrel-exported via index.js):

ServicePurposeSFCC Resource
AssetServiceManage content assetsLibraries
CampaignServiceManage campaignsCampaigns
SlotServiceConfigure slot assignmentsSlot Configurations
ReplicationServiceTrack staging → production syncSites

All services share a common ApiClient (src/infrastructure/sfcc/ApiClient/ApiClient.js) that handles:

  • OAuth 2.0 authentication (via AuthService with disk-based token caching)
  • Rate limiting (3 concurrent, 100ms pacing via RateLimiter)
  • Retry with exponential backoff and Retry-After header support
  • Alphabetically sorted query parameters (for cache-key consistency)
  • Adaptive batch chunking (respects OCAPI 50-subrequest and 5 MB body limits)
  • Client-side in-memory caching (serviceCache, 5 min TTL)

Bulk requests (individual, rate-limited) ​

The application does not use the OCAPI batch endpoint. Bulk operations (fetchMany, batch()) are implemented as individual OCAPI requests run through the same ApiClient.request() path, so they respect rate limiting and retries. This avoids dependency on the OCAPI batch endpoint (many instances do not support it).

javascript
// src/infrastructure/sfcc/ApiClient/ApiClient.js
const results = await apiClient.batch(requests); // N individual rate-limited requests
1

Error Handling ​

OCAPI errors are wrapped in OcapiError for consistent handling:

javascript
// src/infrastructure/sfcc/ApiClient/OcapiError.js
class OcapiError extends Error {
  constructor(statusCode, message, response) {
    super(message);
    this.status = statusCode;
    this.response = response;
  }
}
