Layered Architecture ​

The system follows Clean Architecture principles with clear separation of concerns:

Layer 1: CLI (Presentation) ​

Location: src/cli/

Purpose: Handle user input and output

ComponentResponsibility
index.jsEntry point, command registry dispatch, flag parsing
commands/_middleware.jsShared guards (refresh resolution, dry-run, OCAPI enablement)
commands/handle*.jsIndividual command handlers (thin, delegate to use cases)
cliHelpers.jsUser prompts and confirmations
output/formatters/Unified Output class for CLI formatting (command output + dashboard views)

Design Principles:

  • Thin layer — delegates to use cases
  • Shared middleware eliminates repeated guard patterns across handlers
  • Handles argument parsing and validation
  • Formats output for terminal display
  • CLI-specific presentation logic isolated in output/

Layer 2: Application (Use Cases) ​

Location: src/application/usecases/

Purpose: Orchestrate business workflows

FileClassesResponsibility
ExcelWorkflow/ (index)ParseExcel, CompileRefreshExcel parsing → Refresh DTO → Campaign
DevWorkflow/ (index)GenerateDevFiles, ComposePreview, RefreshOpsDev files, previews, hotfix/delete
SfccWorkflow.jsSyncToSfccSFCC sync, upload, strategy routing
ReportingWorkflow/ (index)GenerateReports, GenerateChangeoutEmail, ManageRegistryReports, emails, registry
HealthCheck.jsHealthCheckOCAPI connectivity verification
BaseUseCase.jsBaseUseCaseThin base (delegates to internal/ helpers)
internal/execution.jssafeCall, safeBatch, retry, withTimeoutExecution primitives
internal/tracking.jscreateTracker, runWithMetricsMetrics and change logging
internal/htmlResolution.jsisHtmlDifferent, resolveHtmlHTML diff and multi-source resolution
ports/OutputPort.jsNullOutputNo-op output port for use cases
ports/PayloadPort.jsNullPayloadBuilder, NullPayloadValidatorPayload port abstractions

Workflow Consolidation:

The use cases are organized into 4 workflow files by domain:

  • ExcelWorkflow - Data ingestion pipeline
  • DevWorkflow - Local development operations
  • SfccWorkflow - SFCC deployment operations
  • ReportingWorkflow - Analytics and registry (40% code reduction via DRY)

Design Principles:

  • Single responsibility per use case
  • Framework-agnostic (no CLI/HTTP dependencies)
  • Depends on domain and infrastructure abstractions

Layer 3: Domain ​

Location: src/domain/

Purpose: Business entities, rules, and pure business logic

EntityResponsibility
CampaignTop-level campaign container
SlotConfigurationSFCC slot binding
ContentAssetHTML content asset
OcapiErrorStructured error type for OCAPI failures (status/message only, from infrastructure API client)
RefreshSchemaZod validation schemas for Refresh DTOs

Validators (in validation.js):

FunctionValidates
validateCampaign()Campaign structure, slots, and date ranges
validateSlot()Slot configuration and asset presence
validateContentAsset()Asset ID and structure
validateRefresh()Refresh DTO structure (Zod schema)

All validators support a strict mode that throws ValidationError on failure:

javascript
// Normal mode - returns { isValid, errors, data }
const result = validateCampaign(campaign);

// Strict mode - throws ValidationError on failure
validateCampaign(campaign, { strict: true });

Dependency Injection ​

BrandContext (Composition Root) ​

Location: src/application/context/BrandContext.js

Purpose: Wire together all dependencies for a brand

javascript
const context = new BrandContext("loft");

// Access use cases
await context.usecases.generateDevFiles.execute(refresh);
await context.usecases.syncToSfcc.execute(campaign);

// Access services
context.fileStore.saveHtml(assetId, html);

// Check OCAPI status
if (context.isEnabled()) {
  await context.usecases.syncToSfcc.execute(campaign);
}

// Diagnostic methods
await context.healthCheck();

Key Design Patterns ​

1. Composition Root (BrandContext) ​

All dependencies wired in one place:

javascript
class BrandContext {
  constructor(brandKey) {
    this.fileStore = new FileSystemStore(this);
    this.apiClient = new ApiClient({...});
    // Use cases are the primary interface for operations
    this.usecases = {
      generateDevFiles: new GenerateDevFiles(this),
      syncToSfcc: new SyncToSfcc(this),
      // ...
    };
  }

  // Diagnostic methods only (not business operations)
  async healthCheck() { ... }
}

2. Use Case Pattern ​

Each workflow is a separate use case extending BaseUseCase, which provides:

  • ExecutionTracker — consolidated metrics collection and change logging (this.tracker)
  • Error handling with retry logic (this.safeBatch(), this.retry())
  • Campaign validation (this.validateCampaign())
  • HTML resolution helpers (this.resolveHtml(), this.isHtmlDifferent())
  • Timeout wrapping (this.withTimeout())

BaseUseCase is deliberately thin — it delegates to extracted modules in internal/ for testability.

javascript
class GenerateDevFiles extends BaseUseCase {
  async execute(refresh, options) {
    // 1. Compile refresh to campaign
    const campaign = await this.brand.usecases.compileRefresh.execute(refresh);

    // 2. Generate files
    // 3. Return result with this.tracker metrics
  }
}

Rules:

  • Files within a barrel folder use relative ./ paths to each other (internal wiring).
  • Files outside the folder import via the barrel only (e.g., require("../../config")).
  • asset.config.js is internal to config — only consumed by slots.config.js, not exported from the barrel.
  • Exception: utils/helpers/action.js, ipid.js, and excel.js import directly from config/app.config (not the barrel) to avoid a circular dependency: config/index.js → slots.config → utils/helpers → config/index.js.

6. Shared Excel Header Aliases ​

Excel column-to-field mapping is defined once in src/config/excel.config.js via the HEADER_ALIASES constant. All brands share the same aliases, which simplifies maintenance and ensures consistency:

javascript
// src/config/excel.config.js
const HEADER_ALIASES = Object.freeze({
  STATUS: ["STATUS"],
  REFRESH_NAME: ["REFRESH_NAME", "REFRESH NAME", "PROJECT SUMMARY"],
  ASSET_TYPE: ["ASSET_TYPE", "ASSET TYPE"],
  // ... all 21 canonical field mappings
});

How it works:

  1. HEADER_ALIASES maps canonical field names to arrays of accepted Excel column names (aliases).
  2. getAliasLookupForBrand(brandId) (in utils/helpers/excel.js) builds a reverse lookup from alias → canonical field.
  3. ExcelParser uses this lookup via buildHeaderMap() to map whatever column names appear in the Excel file to internal field names.
  4. To support a new column naming convention, add it to the relevant field's alias array in excel.config.js.

7. OCAPI Runtime Configuration ​

All OCAPI tuning constants are centralized in OCAPI_RUNTIME (inside src/config/sfcc.config.js). These are hardcoded values — not environment variables — because they rarely change and apply universally:

ConstantDefaultPurpose
maxConcurrent3Max parallel OCAPI requests
minTimeMs100Minimum gap between requests (ms)
requestTimeoutMs30,000HTTP timeout for API calls
authTimeoutMs20,000HTTP timeout for token fetch
maxRetries3API request retry attempts
retryDelayMs1,000Base retry delay (ms)

safeBatchLimit5Use-case batch concurrency

Per SFCC documentation, Data API requests are never cached server-side (making our client-side cache especially valuable), and SFCC uses load shedding (503/429) rather than traditional rate limiting.

OCAPI best-practices compliance:

  • Rate-limited bulk requests: The app does not use the OCAPI batch endpoint (many instances do not support it). ApiClient.batch() runs individual OCAPI requests through the same rate limiter and retry logic; bulk fetch/save are chunked by batchChunkSize (50) for orderly execution.
  • Narrowed select fields: Search queries use specific select fields (e.g. (id,name,c_body) for assets, (configuration_id,slot_id) for slots) instead of (**) to minimize payload sizes and SFCC processing overhead.
  • Sorted query parameters: All outgoing requests sort query parameters alphabetically via a paramsSerializer on the axios instance, following the OCAPI cache-key best practice.

Consumers (ApiClient, AuthService, serviceCache, BrandContext, BaseUseCase) import these constants via the config barrel.

Token persistence: AuthService caches the OAuth token to dev-env/.token-cache.json (gitignored) so consecutive CLI invocations reuse the same token instead of fetching a new one each time. On startup, AuthService reads the cached token from disk; if it's still valid (with the safety window), it skips the auth call entirely. The cache is cleared on invalidateToken() or reset().

8. Registry Fallback Pattern ​

When composing multi-zone assets, the system intelligently handles unchanged zones:

javascript
// ComposePreview.js - getHtml helper
const getHtml = (assetId, zoneAsset) => {
  // 1. Try current refresh folder first
  let html = this._loadHtmlFromPreview(refreshDir, assetId);
  if (html) return html;

  // 2. Fallback: lookup registry for this zone
  const regEntry = registry[assetType]?.[zoneKey];
  if (regEntry?.currentAssetId) {
    // Load from previous refresh where zone was last changed
    html = this._loadHtmlFromPreview(registeredRefreshDir, regEntry.currentAssetId);
  }
  return html;
};

Asset Configuration (asset.config.js + slots/*) ​

Asset types are defined in src/config/asset.config.js with a simplified schema using two key fields:

  • active: Is this asset type processed by automation?
  • mode: "TEMPLATE" (auto-generate HTML) or "DEVELOPER" (manual HTML)

All other behaviors are derived from these two fields.

javascript
// src/config/asset.config.js — ASSET_TYPES
const ASSET_TYPES = {
