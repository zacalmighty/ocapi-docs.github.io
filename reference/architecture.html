Layered Architecture ​
The system follows Clean Architecture principles with clear separation of concerns:
Layer 1: CLI (Presentation) ​
Location: src/cli/
Purpose: Handle user input and output
ComponentResponsibility
index.jsEntry point, command routing, flag parsing, setup flows
commands/*.jsIndividual command handlers (thin, delegate to use cases)
output/formatters.jsUnified Output class for CLI formatting (command output + dashboard views)
Design Principles:
  • Thin layer - delegates to use cases
  • Handles argument parsing and validation
  • Formats output for terminal display
  • CLI-specific presentation logic isolated in output/
  • Command handlers keep side effects localized and delegate to use cases
Layer 2: Application (Use Cases) ​
Location: src/application/usecases/
Purpose: Orchestrate business workflows
FileClassesResponsibility
ExcelWorkflow.jsParseExcel, CompileRefreshExcel parsing → Refresh DTO → Campaign
DevWorkflow.jsGenerateDevFiles, ComposePreview, RefreshOpsDev files, previews, hotfix/delete
SfccWorkflow.jsSyncToSfccSFCC sync, upload, strategy routing
ReportingWorkflow.jsGenerateReports, GenerateChangeoutEmail, ManageRegistryReports, emails, registry
HealthCheck.jsHealthCheckOCAPI connectivity verification
BaseUseCase.jsBaseUseCaseShared use case functionality
Workflow Consolidation:
The use cases are organized into 4 workflow files by domain:
  • ExcelWorkflow - Data ingestion pipeline
  • DevWorkflow - Local development operations
  • SfccWorkflow - SFCC deployment operations
  • ReportingWorkflow - Analytics and registry (40% code reduction via DRY)
Design Principles:
  • Single responsibility per use case
  • Framework-agnostic (no CLI/HTTP dependencies)
  • Depends on domain and infrastructure abstractions
Layer 3: Domain ​
Location: src/domain/
Purpose: Business entities, rules, and pure business logic
EntityResponsibility
CampaignTop-level campaign container
SlotConfigurationSFCC slot binding
ContentAssetHTML content asset
OcapiErrorStructured error type for OCAPI failures (status/message only, from infrastructure API client)
RefreshSchemaZod validation schemas for Refresh DTOs
Validators (in validation.js):
FunctionValidates
validateCampaign()Campaign structure, slots, and date ranges
validateSlot()Slot configuration and asset presence
validateContentAsset()Asset ID and structure
validateRefresh()Refresh DTO structure (Zod schema)
All validators support a strict mode that throws ValidationError on failure:
javascript
// Normal mode - returns { isValid, errors, data }
const result = validateCampaign(campaign);

// Strict mode - throws ValidationError on failure
validateCampaign(campaign, { strict: true });

Dependency Injection ​
BrandContext (Composition Root) ​
Location: src/application/context/BrandContext.js
Purpose: Wire together all dependencies for a brand
javascript
const context = new BrandContext("loft");

// Access use cases
await context.usecases.generateDevFiles.execute(refresh);
await context.usecases.syncToSfcc.execute(campaign);

// Access services
context.fileStore.saveHtml(assetId, html);

// Check OCAPI status
if (context.isEnabled()) {
  await context.usecases.syncToSfcc.execute(campaign);
}

// Diagnostic methods
await context.healthCheck();

All dependencies wired in one place:

class BrandContext {

    this.fileStore = new FileSystemStore(this);

  // Diagnostic methods only (not business operations)

5. Registry Fallback Pattern ​
When composing multi-zone assets, the system intelligently handles unchanged zones:
javascript
// ComposePreview.js - getHtml helper
const getHtml = (assetId, zoneAsset) => {
  // 1. Try current refresh folder first
  let html = this._loadHtmlFromPreview(refreshDir, assetId);
  if (html) return html;

  // 2. Fallback: lookup registry for this zone
  const regEntry = registry[assetType]?.[zoneKey];
  if (regEntry?.currentAssetId) {
    // Load from previous refresh where zone was last changed
    html = this._loadHtmlFromPreview(registeredRefreshDir, regEntry.currentAssetId);
  }
  return html;
};

  4. Composed output includes ALL zones (current + inherited)

Benefits of this approach:
  • Resources loaded ONCE (no duplicates across zones)
  • Single source of truth for validation
  • Zone templates stay clean (pure content)
  • Auto-generated header in composed output
How it works:
  1. slots.config.js defines allowed resources per asset type
  2. ZoneComposer (in RenderingEngine.js) generates header HTML from config
  3. TemplateValidator checks templates against config
  4. Resources in config = INFO (will be auto-generated)
  5. Resources not in config = WARNING (add to config or inline)
Adding a New Use Case ​
  1. Create class extending BaseUseCase
  2. Add to BrandContext._initUseCases()
  3. Create CLI command if needed
  4. Add Makefile target if needed

Mode Configuration ​
The mode field in ASSET_TYPES determines behavior:
ModeDescriptionAuto-Regen on UPDATERequires Explicit Action

Configuration Reference ​
slots.config.js - Unified Asset Type Configuration ​
Asset types are configured with a simplified schema using two key fields:
  • active: Is this asset type processed by automation?
  • mode: "TEMPLATE" (auto-generate HTML) or "DEVELOPER" (manual HTML)
All other behaviors are derived from these two fields.
javascript
// ASSET_TYPES - Unified configuration (simplified schema)
const ASSET_TYPES = {
  // ACTIVE - Template-driven (auto-process)
  PPH: {
    active: true,
    mode: "TEMPLATE",
    slotId: "global-promotion-banner",
    template: "pph/template",
  },

  // ACTIVE - Developer-controlled (explicit action required)
  HOMEPAGE: {
    active: true,
    mode: "DEVELOPER",
    slotId: "hp-contentslot1-hero",
    template: "homepage/template",
    wrapperClass: "g3-hp",         // Composed output wrapped in <div class="g3-hp">
    zones: [
      "HP_MOBILE_CATS", "HP_PROMO_NAV", "HP_TOP_BANNER",
      "HP_HERO", "HP_2T",
      "HP_CAT_IMAGE",
      "HP_DUO", "HP_TRIO",
      "HP_FEATURED_SHOPS", "HP_SLOTS",
      "HP_BOTTOM_BANNER", "HP_RFLK_WIDGET", "HP_UGC_WIDGET",
      "HP_CHARITABLE_HUB_BAR", "HP_LEFT_NAV_CONTENT_SLOT"
    ],
    externalResources: {
      stylesheets: ["webassets/homepage/2024/updated-HP-v8.css"],
      scripts: ["webassets/homepage/2024/gsaptest.js"]
    }
  },

  // INACTIVE - In wireframe but not automated yet
  NFP: {
    active: false,
    mode: "DEVELOPER",
    template: "_default",
    notes: "Non-Full Price - needs dedicated template",
  },
};
