Push behavior: Once a refresh is synced, make push for that refresh exits with "SFCC already has this date; no changes to sync" and does not call OCAPI. When re-pushing with FORCE=1, only changed assets/slots are synced; slot binding is skipped if nothing changed. Use make push FORCE=1 to re-push (e.g. after hotfix). Normal next steps after push are make replicate → make done → make commit.

Daily use vs automation: For normal use, run make pull, make build, make push, etc. with no flags; the app uses the sticky date/refresh and prompts when needed. For scripts and CI, use DATE=, REFRESH=, YES=1, FORCE=1 as needed (e.g. make push DATE=2026-02-14 REFRESH=r1 YES=1).

Producer Commands ​

These 12 commands are the complete producer toolkit.

make setup ​

Interactive configuration wizard. Set brand, data source, and OCAPI toggle with arrow-key selection.

bash
make setup
1

make pull ​

Start of every session. Runs three steps in sequence:

  1. git pull --rebase — sync with teammates
  2. Fetch data from Smartsheet/Excel — parse into refresh files
  3. Show status dashboard — live, ready, build, new dates
  4. Interactive date prompt — pick your working date
bash
make pull                    # Full: git + fetch + status + prompt
make pull SKIP_FETCH=1       # Skip fetch, just git + status
make pull CONVERT=1          # (Smartsheet) Fetch + convert to docs/excel, then parse
1
2
3

make select ​

Set or switch the sticky working selection (date/refresh). Once selected, all subsequent commands use it automatically.

bash
make select                      # Interactive picker
make select DATE=2026-02-14      # Direct set
make select DATE=2026-02-14/r2   # Direct set with refresh
1
2
3

The selection is stored in dev-env/{brand}/.current-date (gitignored — personal to each producer) as YYYY-MM-DD/r#.

Priority order: explicit DATE= > dev-env/{brand}/.current-date > interactive prompt

make build ​

Generate HTML templates and OCAPI payload for the selected refresh.

bash
make build                       # Uses selected date
make build DATE=2026-02-14       # Override for one command
make build DATE=2026-02-14 REFRESH=r2
make build DATE=2026-02-14 ALL=1 # Build all refreshes for the date
1
2
3
4

Build guards prevent accidental overwrites:

StateBehavior
Already syncedBlocked — "Use make build FORCE=1 to force rebuild"
Already builtSkipped — "Use make build FORCE=1 to rebuild, or make push to sync"
New / UpdatedProceeds normally

make build FORCE=1 (force rebuild) ​

Force-rebuild HTML after editing templates. Bypasses build guards.

bash
make build FORCE=1               # Uses selected date
make build DATE=2026-02-14 FORCE=1   # Override date
1
2

Use after editing templates or src/config. Normal make build builds then watches (save any watched file = rebuild).

make preview ​

Generate composed preview output and show SFCC preview links. In TTY mode, preview also offers an interactive template zone picker that opens the dev-env/.../preview/templates/... file in your editor.

bash
make preview                     # Uses selected date
make preview DATE=2026-02-14     # Override
make preview DATE=2026-02-14 REFRESH=r2
1
2
3

make push ​

Validate data quality, validate payload structure, then sync to SFCC staging.

Already-synced guard: If the refresh was already synced (sync-config.json has synced: true), push exits with "SFCC already has this date; no changes to sync" and does not call OCAPI. Use make push FORCE=1 only when you need to re-push (e.g. after a hotfix rebuild). When re-pushing, only changed items are synced; slot binding is skipped if no asset changes.

bash
make push                        # Uses selected date
make push DATE=2026-02-14        # Override
make push DATE=2026-02-14 REFRESH=r2
make push DATE=2026-02-14 ALL=1  # Explicitly sync all refreshes for date
make push DATE=2026-02-14 FORCE=1  # Re-push an already-synced refresh
1
2
3
4
5

If a date has multiple refreshes and no REFRESH=... is provided, push resolves in this order:

  1. Sticky selection for that date (dev-env/{brand}/.current-date)
  2. Interactive refresh picker (TTY)
  3. Error in non-interactive mode requiring explicit REFRESH=... or ALL=1

Validation pipeline (automatic):

  1. Already synced? — If yes, exit with message unless FORCE=1.
  2. Data quality — missing copy, duplicate IPIDs, unknown asset types
  3. Payload structure — campaign, assets, slots all present and valid
  4. Errors block the sync. Warnings open an arrow-picker confirmation (Cancel push / Push anyway). Use YES=1 to skip in non-interactive.
  5. On success, writes status and config to sync-config.json and shows next steps (make replicate, make done, make commit).

make replicate ​

Open manual STG → POD replication checklist for a synced refresh with completion markers.

bash
make replicate
make replicate DATE=2026-02-14
make replicate DATE=2026-02-14 REFRESH=r2
1
2
3

Checklist progress is persisted in sync-config.json under replication.steps.

make done ​

Generate changeout email and verify sync status. Shows next-step hint (make commit).

bash
make done                        # Uses selected date
make done DATE=2026-02-14        # Override
make done DATE=2026-02-14 REFRESH=r2
1
2
3

done only targets synced refreshes. If no synced refresh exists, it warns to run make push.

make commit ​

Stage and commit the selected refresh directory to Git.

bash
make commit                      # Uses selected date
make commit DATE=2026-02-14      # Override
make commit DATE=2026-02-14 REFRESH=r2
1
2
3

Runs:

bash
git add dev-env/{brand}/refreshes/{date}/{refresh}/
git commit -m "{brand} {date} {refresh} done"
1
2

Does not auto-push. Run git push when ready.

make status ​

Unified dashboard for refreshes and next steps.

bash
make status              # Last 14 days + all future; interactive: summary + picker
make status ALL=1        # Show full list (no date window)
1
2

Date window (default): Only refreshes from the last 14 days through all future dates are shown, so the list stays short. Use make status ALL=1 to see every refresh.

In an interactive terminal (TTY):

  • One summary line (e.g. 17 refreshes · 1 live · 2 synced · 1 ready · 13 to build)
  • Then an arrow-key picker: choose a refresh → choose an action (Select, Build, Edit, Preview, Push, Done, Commit). The list is shown once (in the picker only).

When not interactive (e.g. from make pull or when piped):

  • Full table: Date, Name, Status, Next Step
  • Next step shows go-live time when relevant (e.g. → live 2/12 12 AM)
  • Registry summary and footer counts

States: LIVE (today, on site), SYNCED (pushed, future), READY (built, ready to push), BUILD (needs build).

Date States ​

Every refresh progresses through these states:

StateFiles PresentNext Step
NEWrefresh.json onlymake build
READYrefresh.json + ocapi-payload.jsonmake push
SYNCED+ sync-config.json (synced: true)make replicate / make done / make commit (push blocked unless FORCE=1)
