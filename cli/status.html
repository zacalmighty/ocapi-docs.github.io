status ​

Main entry point for web producers. Run make status first. Status states and labels: source src/cli/prompts/stickyDate and status display helpers. If you have no configuration yet, status runs the setup wizard directly (brand, data source, OCAPI) so you can sign in and configure in one go, then continues to the hub. When status then finds no refreshes, it runs a pull and re-checks SFCC so LIVE/SYNCED appear. Interactive hub: pick refresh → pick action → run → back to board. make pull fetches data and auto-builds, then opens this same hub. If you run make status and there are no refreshes yet, status runs a pull for you and then shows the board.

Unified refresh dashboard for the active brand. Shows a short, focused list and lets you pick a refresh and run an action. Refresh labels include the go-live time from the campaign (e.g. r1 - 3pm, r2 - 3am).

Usage ​

bash
make status              # Last 14 days + future; interactive hub with loop
make status ALL=1        # Show full list (no date window)
make status NO_CACHE=1   # Force fresh Smartsheet download when refreshing

When there are no refreshes, status runs a pull for you and then shows the board — but only if the last such pull was more than 30 minutes ago (throttled, no message). Otherwise, run make pull to fetch data first.

LIVE / SYNCED vs READY: Rows show READY when the refresh is built locally but not yet pushed to SFCC. After you push (or after campaigns already exist on SFCC), status checks SFCC and upgrades those rows to SYNCED or LIVE and stores that in the refresh.json sync section. That SFCC check runs when you open status if (1) no row is yet SYNCED/LIVE (so we try once to discover them), or (2) the last check was over 30 minutes ago.

Date window ​

By default only refreshes from the last 14 days through all future dates are shown, so you don't scroll through a long list of past dates. Use make status ALL=1 to see every refresh.

Current live and time ranges ​

Current live is the one refresh on the homepage right now, by time window. When the wireframe (Excel) has both start and end times, status finds the refresh whose window contains the current time; that row is shown as LIVE. At most one row is LIVE.

When a refresh has both start and end times, the board shows a time range on the row (e.g. 2/13 3pm – 2/15 12am) instead of a single date. That explains why there might be no row for a given calendar day—another refresh’s window covers that period. When Excel has start/end set, the board shows these ranges. Excel time-only values are interpreted as UTC; the status board displays them in your local time.

Interactive Hub ​

When you run make status in a terminal, it opens an interactive hub that loops:

  1. Refresh picker — The LIVE refresh (on the homepage now) is first, then your selected refresh, then the rest. Each row shows date, refresh label with time (e.g. r1 - 3pm), name, and status. The row you're working on is marked ← selected; the one on the site now is shown as LIVE.
  2. Action picker — After selecting a refresh, choose an action:
    • Build refresh — Build selected refresh output/payload
    • Push to staging — Sync to SFCC. If data quality errors block, a recovery picker offers: Open files, Re-check, Force push anyway (bypass data quality), Pull, or Back.
    • Upload assets — Run asset-only upload for selected refresh
    • Delete refresh — Remove selected refresh (local/SFCC based on options)
    • Refresh detail (zones + IPIDs) — Run per-date report visibility output
    • Pull (refresh data) — Re-fetch data and auto-build new dates, then refresh the board
  3. Action execution — Runs the selected action
  4. Return to board — After action completes, returns to refresh picker

Pressing q on the action picker returns to the refresh picker. Pressing q on the refresh picker exits.

Picking a refresh sets it as your sticky selection; subsequent commands (make refresh, make push, etc.) use it automatically.

No-TTY fallback ​

When status runs without a TTY (e.g. piped output or CI), it falls back to a table view: Date, Name, Status, plus registry summary and footer. No interactive hub is shown.

For scripts: make status ARGS="--no-interactive" forces table-only output even in a TTY. When running push from scripts or CI, use --yes (or YES=1) to skip confirmation prompts (e.g. data quality warnings).

Replay (one action by index) ​

When running non-interactively, you can run one action and exit by setting:

  • STATUS_REFRESH_INDEX — index of the refresh in the list (0-based)
  • STATUS_ACTION_INDEX — index of the action. Order is defined in src/cli/commands/statusInteractive.js (STATUS_ACTIONS): 0 = Build refresh, 1 = Push to staging, 2 = Upload assets, 3 = Delete refresh, 4 = Refresh detail (zones + IPIDs), 5 = Pull (refresh data)

Example: STATUS_REFRESH_INDEX=2 STATUS_ACTION_INDEX=1 make status selects the third refresh, runs Push, then exits. This is for scripts and tests; normal make status usage is unchanged. For the full list of Make variables (including STATUS_*), see Commands Reference — Make variables.

Sync state and OCAPI ​

When OCAPI is enabled, make status uses SFCC as the source of truth for sync state:

  • Refreshes that have no local sync record but exist on SFCC are shown as SYNCED/LIVE and local state is updated.
  • Refreshes that are marked SYNCED/LIVE locally are checked against SFCC; if the campaign no longer exists on SFCC, state is downgraded to READY and local sync config is updated.

So after cloning the repo or moving to another machine, running make status once will align the dashboard with what’s actually on SFCC.

OCAPI best practices (throttling) ​

Per Salesforce OCAPI Performance Best Practices, Data API requests cannot be cached by the platform and should be used sparingly. To limit load:

  • SFCC check is throttled — Status only calls the Data API (enrich/verify campaigns) at most once every 30 minutes. Other runs use the last known local sync state. Optional env: STATUS_SFCC_CHECK_COOLDOWN_MS to change the throttle window.

States ​

StateCondition
LIVESynced and on site now: folder date is today, or current time is inside the refresh’s start–end window (folder = nominal start; end shows the span)
SYNCEDSynced but not currently live (outside window and/or date not today)
UPDATEDPreviously synced but new source data since last push (needs rebuild)
READYocapi-payload.json exists, not yet pushed
BUILDrefresh.json exists but no payload
NEWData fetched, not yet built (same as BUILD)

Definitions are canonical in Glossary — Status States. Status uses local sync state first (from the refresh.json sync section in each refresh folder). When OCAPI is enabled, it also checks SFCC: if a refresh's campaign exists on the site, that row is shown as SYNCED or LIVE even when local state is missing (e.g. after deleting dev-env). Any state learned from SFCC is written back to local automatically, so the next run (or build guards) can use it without re-querying SFCC.
