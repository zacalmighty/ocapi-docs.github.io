Refresh & Campaign ​

The Refresh and Campaign are the two core data structures in the system. Understanding how they relate is key to understanding the entire automation workflow.

Refresh DTO ​

A Refresh is a Data Transfer Object (DTO) that represents the raw wireframe data for a single refresh date. It's what comes out of the Excel/Smartsheet parser.

Structure ​

json
{
  "date": "2026-02-03",
  "refreshId": "r1",
  "brand": "loft",
  "assetTypes": {
    "HOMEPAGE": {
      "HP_TOP_BANNER": {
        "action": "LAUNCH",
        "headline": "New Arrivals",
        "copy": "Shop the latest styles",
        "cta": "Shop Now",
        "link": "/new-arrivals"
      },
      "HP_HERO": {
        "action": "UPDATE",
        "headline": "Updated Content"
      }
    },
    "PPH": {
      "MAIN": {
        "action": "LAUNCH",
        "slides": [...]
      }
    }
  }
}

Key Properties ​

PropertyDescription
dateThe target go-live date (YYYY-MM-DD)
refreshIdOrdinal identifier within the date (r1, r2, r3)

assetTypesMap of asset type → zone → content data

Validation ​

Refresh DTOs are validated using Zod schemas defined in src/domain/validation.js:

javascript
const { validateRefresh } = require('./domain/validation');

const result = validateRefresh(data);
if (!result.success) {
  console.error(result.error.issues);
}

Campaign Entity ​

A Campaign is the top-level domain entity that represents a time-bound promotional campaign in SFCC. It's the result of compiling a Refresh DTO.

Structure ​

javascript
Campaign {
  campaign_id: "loft-2026-02-03-r1",
  name: "LOFT February 3 Refresh 1",
  description: "Automated campaign for 2026-02-03",
  enabled: true,
  start_date: "2026-02-03T00:00:00.000Z",
  end_date: "2026-02-10T00:00:00.000Z",
  slots: [
    SlotConfiguration { ... },
    SlotConfiguration { ... }
  ]
}

The Transformation ​

The CompileRefresh use case transforms a Refresh DTO into a Campaign entity:

What CompileRefresh Does ​

  1. Creates Campaign metadata — ID, name, dates from refresh data
  2. Builds SlotConfigurations — One per zone in the refresh
  3. Resolves Asset IDs — Based on action type and registry
  4. Handles Asset Reuse — NO_CHANGE items reuse existing assets
  5. Registers New Assets — LAUNCH items get new asset IDs

Campaign ID Format ​

Campaign IDs follow a predictable pattern:

{brand}-{date}-{refreshId}
1

Examples:

  • loft-2026-02-03-r1
  • ann-2026-01-15-r2

Asset ID Format ​

Content asset IDs include the zone information:

{brand}-{date}-{refreshId}-{assetType}-{zone}
1

Examples:

  • loft-2026-02-03-r1-homepage-hp_top_banner
  • ann-2026-01-15-r2-pph-main

Refresh Lifecycle States ​

Each refresh progresses through a lifecycle tracked by on-disk files:

StateIndicatorDescription
NEW / BUILDrefresh.json exists, no payloadData parsed from Excel; needs make build
READYocapi-payload.json existsBuilt and ready to push to SFCC
SYNCEDsync-config.json has synced: truePushed to SFCC staging
UPDATED (stale)sync-config.json has synced: true AND stale: trueA make pull brought new data for an already-synced refresh. Build and push proceed automatically without FORCE=1.
LIVESynced + date is todayCampaign is active on the storefront

The UPDATED state is set automatically by saveRefresh when it detects that the source data changed for a previously-synced refresh. After a successful make push, the stale flag is cleared and the refresh returns to SYNCED.

File Storage ​

Both structures are persisted to the filesystem:

dev-env/{brand}/refreshes/{date}/{refreshId}/
├── refresh.json           # Original Refresh DTO
├── ocapi-payload.json     # Campaign serialized for OCAPI
├── sync-config.json       # Sync state (synced, stale, lastSyncedAt, etc.)
├── assets/
│   └── {asset-id}.json    # Individual asset data
└── preview/
    ├── templates/         # Handlebars templates
    └── rendered/          # Generated HTML
