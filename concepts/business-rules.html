Business Rules Breakdown ​

If you only remember 3 things

  1. Date + refreshId = one campaign. A date can have multiple refreshes (r1, r2, r3).
  2. Homepage is zone-based. Each zone gets its own SFCC asset; the composed homepage.html is preview-only.
  3. The registry decides reuse vs new ID. NO_CHANGE and UPDATE look up existing IDs; LAUNCH always creates a new one.

The system solves one big problem: automate SFCC campaign management from Excel to production. This page decomposes that into 8 smaller domains, each with its own rules and diagrams.

Build Guards (Sections 1–3) ​

How Excel data is parsed, normalized, and resolved into actionable refresh DTOs.

1. Excel Parsing ​

Problem: Raw Excel files have inconsistent formats, mixed headers, and hierarchical rows.

Solution: Detect format → normalize headers → group rows → assign refresh IDs → fill gaps.

What producers should do: Use the CONVERTED wireframe format (REFRESH_NAME, REFRESH_DATE, ACTION, ASSET_TYPE) or ensure your sheet headers match the alias list; enter times in UTC or account for timezone offset.

Edge cases: Unknown sheet format → parser returns no refreshes. Unknown action (e.g. SKIP, HOTFIX) → one-time warning, then NO_CHANGE. Missing end time → inferred from next refresh or end of day (UTC).

Rule: Format Detection

The parser auto-detects which Excel format is in use by scanning the header row:

FormatRequired HeadersWhen Used
CONVERTEDREFRESH_NAME, REFRESH_DATE, ACTION, ASSET_TYPEGolden test files (normalized format)
BANNERWEB_PROD_CODED, DEVICE, ACTION, ASSET_TYPERaw Smartsheet exports
FLAT_TIMEDREFRESH_DATE, START_DATETIME, ACTIONTime-based refreshes
Rule: Header Alias Resolution

Excel headers vary across teams. The parser maps them to canonical keys:

"PLACEMENT NOTES\PPH MESSAGE\DISCLAIMER" → COPY_MESSAGE
"LAUNCH/REMOVE"                          → ACTION
"MOBILE/DESKTOP"                         → DEVICE
"LINK TRACKING"                          → LINK_TRACKING

Rule: Parent-Child Row Grouping
  • Parent row: Has REFRESH_NAME + REFRESH_DATE, no ASSET_TYPE
  • Child row: Inherits parent's date/time, has its own ASSET_TYPE + zone data
Rule: Refresh ID Assignment

Multiple refreshes on the same date get sequential IDs based on start time:

Date: 2026-02-08
  Refresh at 06:00 → r1
  Refresh at 12:00 → r2
  Refresh at 18:00 → r3

Rule: End Time Inference

If a refresh has no end time, it's inferred from the next refresh:

r1: 06:00 – ?     → r1: 06:00 – 11:59  (next start - 1 min)
r2: 12:00 – ?     → r2: 12:00 – 17:59
r3: 18:00 – ?     → r3: 18:00 – 23:59  (last = end of day)

All times are interpreted as UTC. The parser uses setUTCHours for all date/time operations. If your brand operates in a non-UTC timezone, account for the offset in your wireframe times.

Rule: Action Normalization

Raw Excel values are normalized to 4 canonical actions:

Raw InputCanonical Action
LAUNCH, NEW, CREATE, ADDLAUNCH
UPDATE, EDIT, MODIFY, CHANGEUPDATE
REMOVE, DELETE, DROPREMOVE
NO_CHANGE, NO CHANGE, NO CHANGE/LINK SAME, REUSE, (empty)NO_CHANGE

Any other value triggers an unknown-action warning and defaults to NO_CHANGE.

Edge cases: Unknown action (e.g. SKIP, HOTFIX) → one-time warning, then NO_CHANGE. Empty or missing end time → inferred from next refresh's start or end of day (UTC).

2. Asset Type Resolution ​

Problem: Excel uses dozens of names for the same thing ("CAT A", "CAT B", "SLOT 1:", "PPH-a").

Solution: Three-stage resolution: direct match → pattern match → zone consolidation.

What producers should do: Use the zone names from the table above (e.g. TOP BANNER → HP_TOP_BANNER) so resolution is predictable; avoid ad-hoc names that do not match patterns.

Edge cases: Unknown asset type → logged; not in asset/slots config → data quality warning at push. Inactive types (NFP, FP, etc.) are parsed but skipped for HTML generation.

Rule: Direct & Pattern Matching

Excel names are resolved via direct key match, underscore/space normalization, and ASSET_TYPE_PATTERNS (first match wins).

Excel NameResolves To
HOME PAGE, HPHOMEPAGE
PPH A, PPH B, PPH CPPH
PLP HEADER, HEADERPLP_HEADER
DISCLAIMER, POP UPPOPUP
COUPON PAGE, HTML COPYCOUPONS

Rule: Active vs Inactive Asset Types

Not all asset types are automated:

Inactive types are excluded because they either lack HTML templates, are managed by another system, or are not yet supported. They are still parsed from the wireframe for reporting and validation.

Edge cases: Unknown asset type (no direct or pattern match) → logged; not in asset/slots config → data quality warning at push.

3. Action Types ​

Problem: Each zone in a refresh can need different handling: new content, updated content, removed content, or no change.

Solution: 4 action types that control asset ID generation, HTML rendering, and SFCC sync behavior.

What producers should do: Use only LAUNCH, UPDATE, REMOVE, or NO_CHANGE (and documented aliases) in the wireframe; use make build FORCE=1 for a force rebuild, not a wireframe action.

Edge cases: SKIP/HOTFIX or any unknown value → one-time warning, then NO_CHANGE. Zero-length time window (start = end) → refresh is considered live from start time for status LIVE.

Rule: Action Comparison Matrix
New ID?Regen HTML?Sync?Registry
LAUNCHYesYesYesRegister
UPDATENoYes*YesTouch
REMOVEN/ANoDeleteUnregister
NO_CHANGENoNoNoNo change

*HTML regeneration on UPDATE depends on the asset's mode (see Section 6).

Force rebuild: To force-regenerate HTML and re-sync regardless of action, use make build FORCE=1 then make push FORCE=1. This is a CLI workflow, not a wireframe action.

Edge cases: Zero-length time window (start = end) → that refresh is considered live from start time for status LIVE. Values such as SKIP or HOTFIX are not in the action config → normalized to NO_CHANGE with a warning.

Rule: Dominant Action

When a zone has multiple items with different actions, the highest-priority action wins:

LAUNCH > UPDATE > REMOVE > NO_CHANGE

Asset Resolution (Sections 4–6) ​

How asset IDs are generated, the registry tracks what's live, and HTML rendering is decided.

4. Asset ID Generation ​

Problem: Every SFCC content asset needs a unique, deterministic ID.

Solution: Structured naming convention based on brand, date, refresh, type, and zone.

What producers should do: No direct action; IDs are generated from wireframe date, refresh, and zone. Ensure date and refresh are correct so asset IDs stay consistent across runs.

Edge cases: Single-zone types omit zone from ID. Multi-zone types require zone key. Invalid or duplicate IDs are validated at push.

Rule: ID Naming Convention

Single-zone types (PPH, POPUP, COUPONS):

{brand}-{date}-{refreshId}-{type}
→ loft-2026-02-08-r1-pph
1
2

Multi-zone types (HOMEPAGE zones):

{brand}-{date}-{refreshId}-{type}-{zone}
→ loft-2026-02-08-r1-homepage-hp-hero
1
2

Campaign ID:

{brand}-{date}-{refreshId}
→ loft-2026-02-08-r1
1
2

Slugification rules:

  • Lowercase everything
  • Replace spaces and underscores with hyphens
  • Strip special characters
  • Example: HP_MOBILE_CATS → hp-mobile-cats
Rule: Template & Rendered File Naming

Template files use the zone shorthand (not the full asset ID):

preview/templates/homepage/hp-hero.html       ← zone shorthand
preview/templates/homepage/hp-mobile-cats.html
preview/templates/pph/pph.html                ← single-zone: type as name
1
2
3

The full SFCC asset ID is in the @asset: comment at the top of each template file.

Rendered (composed) files use the asset type as the filename:

preview/rendered/homepage.html    ← all zones composed together
preview/rendered/pph.html         ← single-zone rendered
1
2

Each has an <!-- asset: ... --> comment at the top identifying the SFCC asset.

5. Registry Lifecycle ​

Problem: We need to know what's currently live in SFCC to handle UPDATE, NO_CHANGE, and zone carry-forward.

Solution: A per-brand JSON registry that tracks the current asset ID for each zone.

What producers should do: Run make registry to view or bootstrap the registry; after cloning or first run, the system can auto-seed from the first refresh. Do not edit asset-registry.json by hand unless instructed.

Edge cases: First run with empty registry → auto-bootstrap creates new IDs for NO_CHANGE/UPDATE zones. REMOVE unregisters the zone; next LAUNCH for that zone gets a new ID.

Rule: Registry Operations
OperationTriggerWhat Happens
RegisterLAUNCH actionStores new asset ID, date, refresh ID
ReuseUPDATE/NO_CHANGEReturns existing asset ID from registry
TouchUPDATEUpdates lastUpdated timestamp
UnregisterREMOVE actionRemoves zone entry
BootstrapFirst run or make registryScans filesystem, populates registry
Carry-forwardZone not in current refreshLoads HTML from previous refresh for composition
Rule: First-Run Bootstrap

On the very first run with an empty registry, zones with NO_CHANGE or UPDATE that have no registry entry are auto-bootstrapped: a new asset ID is created, the effective action becomes LAUNCH, and the zone is registered.

Output: Initialized: N zones (first run) — shown once as a summary, no per-zone warnings.

Rule: Carry-Forward for Composition

When composing the homepage, zones not in the current refresh are pulled from the registry. For example, if refresh r1 includes HP_HERO, HP_TOP_BANNER, and HP_2T, the registry supplies the remaining zones (HP_MOBILE_CATS, HP_PROMO_NAV, HP_SLOTS, etc.) from whichever previous refresh last touched them. The composed homepage.html always includes ALL zones.

6. HTML Rendering ​

Problem: Different asset types need different rendering strategies — some are fully automated, others are manually authored.

Solution: Two modes (TEMPLATE vs DEVELOPER) that control when HTML is regenerated.

What producers should do: For TEMPLATE types (PPH, POPUP, etc.), edit the wireframe and run make build. For DEVELOPER types (HOMEPAGE, PLP_HEADER), edit HTML in preview/templates and use make build FORCE=1 when you want to re-sync after template-only changes.

Edge cases: UPDATE in DEVELOPER mode preserves existing HTML unless FORCE=1. NO_CHANGE never regenerates HTML. REMOVE skips rendering.

Rule: Mode Assignment
ModeAsset TypesBehavior
TEMPLATEPPH, POPUP, COUPONS, HDRHTML regenerated on every LAUNCH/UPDATE
DEVELOPERHOMEPAGE, PLP_HEADERHTML only regenerated on LAUNCH; UPDATE preserves manual edits

To force-regenerate in DEVELOPER mode, use make build FORCE=1.

Rule: Rendering Pipeline
  1. Template Resolution: Zone template → type template → _default.html (fallback chain)
  2. Data Context: Items from refresh.json → Handlebars context with @asset, @data-source, @zone comments
  3. Render: Compile Handlebars template with data → per-zone template file (e.g. hp-hero.html)
  4. Compose (multi-zone): Load all zone templates → add zone separator comments → inject external CSS/JS resources → wrap in container div → composed rendered file (e.g. homepage.html)
Rule: Zone Composition Detail

For multi-zone types like HOMEPAGE, the composer:

  1. Loads each zone's template HTML from preview/templates/homepage/
  2. Adds metadata comments between zones:
    html
    <!-- ZONE: HP_HERO | template: T5 (Knockout 3-Col) | action: LAUNCH | asset: loft-2026-02-08-r1-homepage-hp-hero -->
    1
  3. Injects external CSS/JS in the header (from externalResources config)
  4. Wraps in container div with wrapperClass (e.g., g3-hp)
  5. Prepends asset identification comment:
    html
    <!-- preview: composed HOMEPAGE | date: 2026-02-08 | refresh: r1 | zones: 11 -->
    1

Preview vs SFCC

The composed homepage.html is a preview-only file for local review. It is NOT synced to SFCC as a single asset. Each zone has its own asset ID (e.g., loft-2026-02-08-r1-homepage-hp-hero) and is synced individually as a separate SFCC content asset. You will not find a single "homepage" asset in Business Manager — look for the zone-level assets instead.

Rule: Hero Template Variant Detection

The composer auto-detects which hero template variant is active by scanning CSS classes:

CSS ClassDetected VariantBrand
g3-hero--v1T1 (Video Hero)LOFT
g3-hero--ko-3T5 (Knockout 3-Col)LOFT
g3-hero--toggle-fiveT12 (Toggle Five)LOFT

Push Validation (Section 7) ​

How refresh data is transformed into OCAPI-compatible payloads for SFCC.

7. Campaign & Slot Building ​

Problem: SFCC needs structured payloads: campaigns, content assets, slot configurations, and slot bindings.

Solution: Transform refresh data into OCAPI-compatible JSON payloads.

What producers should do: Run make build to generate ocapi-payload.json; slot configs and bindings are derived from asset/slots config. Use make push to sync; the system diffs against last-synced config.

Edge cases: Category fanout creates one slot binding per category. Shorter-duration campaigns get lower rank (higher priority). Strategy routing (content-slot vs plp-callout) is per asset type.

Rule: Category Fanout

Some slots bind to multiple categories (e.g., PLP headers). Each category gets its own slot binding with a unique context_id.

For example, an asset with categoryIds: [cat100, cat200, cat300] produces 3 separate slot bindings, one per category.

Rule: Slot Rank Assignment

Shorter-duration campaigns get higher priority (lower rank number):

Duration 2h  → rank 10
Duration 6h  → rank 15
Duration 24h → rank 20

2
3
Rule: Sync Strategy Routing

Different asset types use different sync strategies:

StrategyAsset TypesBehavior
content-slotPPH, POPUP, HOMEPAGE, etc.Standard OCAPI sync
plp-calloutPLP promotional textSeparate PLP API
dataData-only typesNo sync (data used internally)

Sync Strategy (Section 8 + Cross-Cutting) ​

How payloads are pushed to SFCC with diff detection, retry logic, and cross-cutting workflow rules.

8. Sync to SFCC ​

Problem: Push local changes to SFCC staging without unnecessary API calls.

Solution: Compare local vs remote, only sync differences, with retry logic.

What producers should do: Run make push after make build; use make push FORCE=1 only when re-pushing an already-synced refresh (e.g. after a fix in SFCC). Use make replicate for staging → production steps.

Edge cases: Already synced and not stale → push exits with message; use FORCE=1 to override. Stale (new data since last sync) → push proceeds without FORCE. Retry on 429 and 5xx; no retry on 4xx (except rate limit).

Rule: Retry Logic

Transient failures are retried with exponential backoff:

Attempt 1 → fail → wait 500ms
Attempt 2 → fail → wait 1000ms
Attempt 3 → fail → wait 2000ms
Attempt 4 → throw error
1
2
3
4

Retryable errors: 429 (rate limit), 5xx (server error) Non-retryable errors: 400 (bad request), 401 (auth), 404 (not found)

Rule: Slot Equality Check

Two slot configurations are considered equal if all these fields match:

  • enabled
  • slot_id
  • configuration_id
  • context + context_id
  • rank
  • schedule.start_date + schedule.end_date
  • customer_groups
Rule: Staging → Production

After syncing to staging, production deployment is a manual step:

make push DATE=...        → Syncs to SFCC staging
make replicate            → Shows manual STG → POD replication steps
1

Cross-Cutting Rules ​

Rule: Date Prioritization

make pull → status dashboard → sticky selection (dev-env/{brand}/.current-date) → if multi-refresh, select refresh (interactive or explicit) → proceed with build / preview / push / done / commit.

Rule: Status Visibility

make status shows all discovered refresh entries for the brand (date + refreshId) and labels each as:

  • LIVE (synced)
  • READY (built, pending push)
  • BUILD (fetched, not built)
Rule: Multi-Refresh Handling

Each refresh on the same date (r1, r2, r3) gets its own directory, asset IDs, campaign, and sync status. They are fully independent.

Example:

Date: 2026-02-08
  r1 (06:00–11:59) → separate directory, separate assets, separate sync
  r2 (12:00–17:59) → separate directory, separate assets, separate sync
  r3 (18:00–23:59) → separate directory, separate assets, separate sync
